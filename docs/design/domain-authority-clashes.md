# Domain Engine — second development increment
Baseline: v1.74.0. Development branch, not a release.

## Implemented
- Active GM serializes JJK domain lifecycle, mode/close and reaction decisions through a typed query. Foundry 14 CONFIG.queries provides the authenticated context.user; remote requests without that context are rejected. Arbitrary remote domainUpdate/zone writes were removed. This is module-level validation, not a replacement for Foundry's actor ownership model.
- Domain state records the original token UUID, scene and level. Sure-hit, clash detection, reaction candidates and barrier attacks check matching levels when available. Geometry is a circle and token-center measurement; exact occupied squares, occlusion, volumetric elevation and irregular geometry remain out of scope.
- New Attack Barrier HUD action: select an owned token, enter attack bonus, reach/range and bounded simple damage formula. GM validates cross-owner requests (world playerGMRequests must be enabled), calculates distance to the boundary and inside/outside automatically, rolls against barrier AC, applies existing side multipliers, rejects duplicate operation IDs, and closes broken barriers. Manual HP adjustment is GM-only. This is an explicit GM-reviewed roll workflow, not a targetable Midi-QOL proxy token or an automatic weapon-use/CE/critical-damage/advantage pipeline.
- Reaction offers persisted on the originating actor with opening ID, per-actor pending/claimed/declined/used/expired status, and an exclusive actor claim. Acceptance checks ownership and eligibility. A reaction is confirmed by the actual domain effect. The root waits for outstanding responses before resolving overlapping domains; sure-hit is suspended while the window is open. Windows are reconciled on turn changes, connection changes and periodic active-GM checks. The 120-second fallback and expiry at combat turn change are implementation choices, not a verified V6 rule.
- Six regression scenarios are targeted, including original-token attribution, authorization, level geometry, barrier hit/miss/idempotency, exclusive claims/expiry, and simultaneous group resolution.

## Remaining risks / manual acceptance
- Real Foundry v14 + dnd5e 6.1 + Midi-QOL/DAE multiclient integration is not proven by the single-context mock. Validate socket query user context, actor synthetic token UUIDs, GM handover, actor disconnect/reconnect, and simultaneous activity completion. Existing general CE writes and user-controlled item workflows are not globally transactional; do not claim database-level atomicity. A GM interruption between related document writes can still require repair.
- A reaction that completes after timeout may be treated as a separate expansion; a canceled reaction is consumed for that offer rather than blindly rerun. Validate this policy with the GM.
- Independent overlapping openings and membership changes during an active three-way clash require real-world timing tests and rule verification; prior V6 refinement formulas are preserved. No new per-technique rules or anti-domain mechanics are introduced here.
- Pending windows are restored from persisted flags, not re-created as new prompts after every login; existing chat cards remain actionable until the valid window ends.
- Confirm barrier attack statistics against the attacker's sheet and adjudicate critical damage, advantage/disadvantage, CE cost and action economy manually. Do not treat this as a complete Midi-QOL attack integration.
- No release before CI and explicit approval; update changelog/manifest separately.

## Third increment: wards, HUD and homebrew profiles
Source: Google Drive manual JJK 5e V.6, sections Domain Expansion, Simple Domain, Hollow Wicker Basket, Falling Blossom Emotion and Domain Amplification. The ward implementation is intentionally limited: Hollow Wicker Basket selects the caster plus currently selected nearby token UUIDs, and checks their distance and level; defensive Falling Blossom and Amplification negate guaranteed-hit targets in the attack/save workflow. The actual Midi-QOL multi-client workflow must still be validated. Simple Domain still uses the existing temporary-HP implementation; shared barrier absorption, one damage event per area, overflow, movement cleanup, offensive Falling Blossom and Amplification versus ordinary techniques/Maximum Output remain incomplete. Amplification action economy must be adjudicated manually. Custom domain profiles are GM-approved, manually triggered on selected eligible targets, with bounded dice, native saves, conditions and cleanup. They do not define an entire innate technique or automatically run on initiative 20. Existing per-domain activities are exposed in the HUD; the 77-entry inventory is a semantic QA checklist, not certification. Four additional regression cases passed along with the preceding 83 on GitHub Actions run 45451017664. Real Foundry multi-client playtest remains outstanding.
